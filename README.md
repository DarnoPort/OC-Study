# IGOR — OS Development Study

Репозиторий служит внешней памятью и справочником учебного проекта IGOR, чтобы продолжать обучение в новых чатах без повторного пересказа.

## Проект
- **Название:** IGOR.
- **Цель:** учебная собственная ОС с постепенным освоением принципов ОС.
- **Целевая архитектура:** x86, 32-bit. x86-64 отложена.
- **Michael OS:** отдельный предыдущий проект; использовать как референс, не как целевую ОС.
- **Среда:** Ubuntu доступна и установлена; GCC, GNU ld и NASM проверены.

## Правила обучения
1. Понимание важнее скорости; идти небольшими шагами.
2. Синтаксис C объяснять с нуля, учитывая основной прежний опыт пользователя в Python.
3. Формат: теория → механика → небольшой пример → мягкая проверка → практика → recap.
4. Не выдавать большие листинги без объяснения назначения.
5. Различать «обсуждено» и «подтверждено ответами/практикой».
6. При затруднениях объяснять спокойно; ошибки локализовать, не переписывать проект без причины.
7. После каждого урока обновлять этот README.

## Учебный прогресс

### Урок 0.1 — ОС и загрузка
**Статус:** базовые идеи частично усвоены; углубление потребуется.
- CPU выполняет машинные инструкции и может работать без ОС.
- ОС — привилегированное системное ПО, управляющее ресурсами и предоставляющее сервисы.
- Упрощённая цепочка: CPU reset → BIOS/UEFI → загрузчик → ядро.
- Загрузчик подготавливает загрузку и передаёт управление ядру.
- C-код напрямую не исполняется CPU: компилятор создаёт машинный код; linker связывает объектные файлы; загрузочный механизм подготавливает запуск.
- Пользователь по существу различил роль CPU, ОС, загрузчика и ядра.

### Урок 0.2 — Инструкции, регистры и память
**Статус:** начальное понимание подтверждено ответами.
- Машинные инструкции, регистры EAX/EBX/ECX/EDX/ESP/EBP, `mov`, `add`.
- EIP содержит адрес следующей инструкции; переходы могут изменить поток выполнения.
- RAM моделируется как адрес → содержимое. `mov eax, 0x2000` загружает число/адрес, а `mov eax, [0x2000]` читает память по адресу.
- `0x` — шестнадцатеричная запись; скобки `[]` в Assembly означают обращение к памяти.
- Пользователь правильно решил примеры с регистрами, адресами RAM и различием immediate vs memory operand.

### Уроки 0.2.1–0.2.2 — Основы C и указатели
**Статус:** базовое понимание подтверждено; закреплять по мере практики.
- `int x = 123;`: тип, имя, присваивание, значение; тип влияет на интерпретацию/размер объекта.
- `&x` получает адрес; `int *p` — указатель; `p` хранит адрес, `*p` обращается к объекту по адресу.
- `*p = 100` записывает значение в исходный объект через указатель.
- `int p = x` копирует значение, а `int *p = &x` хранит адрес.
- Пользователь верно определил значения в задачах с указателями. Ранее путал изменение указателя с изменением объекта; отдельно закреплено: `p = &y` меняет адрес в p, но само x не изменяет.

### Урок 0.3 — Функции, стек, `call` и `ret`
**Статус:** базовое понимание подтверждено ответами; подробности calling convention отложены.
- Разобраны функции C, параметры, `return`, стек как LIFO, ESP как адрес вершины стека, EBP как ориентир stack frame в упрощённой модели.
- `push` уменьшает ESP на 4 байта в 32-битном примере; `pop` извлекает верхнее значение.
- `call` сохраняет адрес возврата в стеке и передаёт выполнение функции; `ret` извлекает адрес возврата и загружает его в EIP.
- Пользователь верно объяснил LIFO аналогией с тарелками, правильно определил результаты записи через указатель и ESP после push/call.
- Уточнено: при `call` EIP переходит на функцию; адрес инструкции после call сохраняется для возврата.

### Урок 0.4 — C → 32-bit x86 → ELF → linker
**Статус:** завершён; практическое понимание подтверждено.
- Проверено реальное окружение Ubuntu: GCC 15.2.0, GNU ld 2.46, NASM 3.01.
- Написана и запущена обычная C-программа `hello.c`; увидена разница между C-кодом и машинным кодом.
- Через `gcc -S hello.c` просмотрен Assembly обычной 64-битной Linux-программы: `RAX/RSP/RBP`, вызов `printf`, передача аргумента и возврат.
- Через `gcc -m32 -S` просмотрен 32-битный x86 Assembly; пользователь связал `EAX/ESP/EBP` с выбранной архитектурой.
- Обсуждено, что 64-битное x86 — расширение 32-битного x86: `RAX/RSP/RBP` шире соответствующих `EAX/ESP/EBP`.
- Создан freestanding C-код с `volatile int x = 42` и бесконечным циклом.
- Выполнено `gcc -m32 -ffreestanding -c`; получен `ELF 32-bit LSB relocatable, Intel i386`.
- Через `objdump -d` увидены реальные инструкции `push`, `mov`, `sub`, `call`, `ret`, `jmp`; запись `0x2a` связана с числом 42.
- Выполнено `ld -m elf_i386`; получен `ELF 32-bit executable`, статически связанный ELF-файл.
- Закреплено различие: compiler переводит C в объектный код; linker собирает объектный код в ELF и разрешает связи/размещение.
- Пользователь понял, что аргументы не обязательно передаются через стек: это зависит от ABI. Для рассмотренного 64-bit System V ABI первый аргумент передаётся через `RDI`; 32-bit calling convention ещё не закреплён.
- Полученный ELF всё ещё рассчитан на обычную Linux-среду и не является ядром IGOR; PIC/GOT отложены.

### Урок 0.5 — Каркас IGOR: entry point → загрузка → C
**Статус:** в процессе. Подфаза 0.5.1 завершена и проверена; 0.5.2 ещё не начата.

#### 0.5.1 — Assembly entry point вызывает C
- Создан `lesson-0.5/boot.asm` с `bits 32`, `global _start`, `extern kernel_main`, `cli`, `call kernel_main` и бесконечным `.hang`-циклом через `hlt`/`jmp`.
- Создан `kernel.c` с `void kernel_main(void) { while (1) {} }`.
- Собраны `boot.o` через NASM и `kernel.o` через GCC (`-m32 -ffreestanding -fno-pie -fno-stack-protector`).
- Выполнена линковка: `ld -m elf_i386 -e _start -o kernel.elf boot.o kernel.o`.
- `file kernel.elf` подтвердил: `ELF 32-bit LSB executable, Intel i386, statically linked, not stripped`.
- `objdump -d kernel.elf` подтвердил `_start` по `0x08049000`, `call kernel_main` по `0x08049001`, функцию `kernel_main` по `0x08049009` и её бесконечный цикл.
- Пользователь прислал фактический вывод `file` и `objdump`; сборка и связь Assembly → C подтверждены.
- В `kernel_main` GCC сгенерировал пролог `push %ebp` / `mov %esp,%ebp`, `nop` и бесконечный `jmp`.
- Важно: это пока связанный ELF-файл, **не bootable kernel**. Запуск в QEMU/через загрузчик не выполнялся.

#### Следующая подфаза — 0.5.2: стек ядра и размещение памяти
- Разобрать, почему вызов C требует корректного стека и почему нельзя без проверки полагаться на стек, оставленный загрузчиком.
- Ввести linker script постепенно: размещение секций/символов и связь символов с адресами.
- Затем выделить стек и настроить `ESP` до вызова `kernel_main`; только после понимания перейти к загрузочному механизму.
- Предпочтительно идти небольшими проверяемыми шагами; не перескакивать сразу к большому загрузочному листингу.
